Architecture

One source suite, one reference runner, three deployment paths. Each folder documents its own internals; this is the only page that shows all four at once — and the only place a missing folder, or a rubric missing from one folder, is visible at all.

source of truth reference runner — the instrument deployment path

Why harness/ is not a fourth path

the distinction the rest of the page depends on

It is the instrument

harness/judge_spec.py resolves REPO_ROOT / "judges" and harness/testsets.py resolves data/testsets — live, not vendored. The three folders were ported from it and are validated against it. run_judges is the only runner with a Batches API mode and the only one that can sweep a whole corpus, which makes it the only place an agreement figure could ever come from.

Reading it as a fourth path

You would go looking for an ingest, a write-back, a provisioning verb, a deploy target and a rubrics/ folder. There are none. Its only dependencies are anthropic, pydantic and PyYAML — no boto3, no arize. Nothing in harness/ produces an artifact that any platform consumes, and treating its output as a production score is the one misreading this page exists to prevent.

The vendoring check runs in one direction only

verified by experiment, not inferred

All three folders carry an identical check_drift. It loads rubrics/RUBRIC_PROVENANCE.json, then for each recorded filename it hashes ../judges/<name> and compares. The vendored file sitting next to the manifest is never opened.

$ shasum -a 256 judges/actionability.md                          2d41c72d8a9621ee  source
$ jq -r '.files["actionability.md"]' .../RUBRIC_PROVENANCE.json  2d41c72d8a9621ee  recorded
$ shasum -a 256 agentcore-integration/rubrics/actionability.md   4f82b155a86de680  what deploys

$ bin/agentcore-judges check-drift
in sync with ../judges                                           exit 0

Two blind spots follow from the same shape. data/ is vendored into all three folders as well — 11 testsets, the gold fixtures, all currently byte-identical to the source — and there is no provenance manifest for it at all. No folder’s check-drift covers it in either direction, and with no recorded hash a difference between a copy and the root could not even be attributed to one end or the other — for the very samples every score run grades against. And _scoring-tail-ax.md, the file arize-integration substitutes, appears in no manifest at all: it is the one file on that path with no upstream and no check.

The second thing only the root can see: a whole folder deleted, or a rubric present in two folders and missing from the third, is invisible from inside any single folder. Each check_drift can only iterate the manifest it was handed. Note also that arize-judges check-drift --help describes itself as “fail if the vendored rubrics differ from ../judges”, which is what the code would have to do rather than what it does. A check that answers the other direction, or that notices an absent folder, can only be written here.

Where the offline scorer sits

each path grades its own artifact, not the rubric in the abstract

Every folder now carries a score verb reading its vendored data/testsets/. What differs is what gets scored, and that difference is the point:

  • agentcore-integration scores the prompt built by judge.build_request, through spans.Conversation.render and out through boundary.agentcore_result — the same functions the Lambda calls, imported rather than copied.
  • arize-integration scores the rendered AX template, filled the single-brace way AX fills it, byte-for-byte the string provision uploads.
  • agentcore-native scores TransformReport.instructions — the rewritten text, not the reviewed rubric — against a reconstructed standardization prompt, because the real shape of {context} is undocumented outside an AWS account.

The testsets are model-written and model-labelled, so agreement with them is agreement with a model that read the same rubric. They are a regression instrument, not a validity claim. harness/testsets.py validate reports 68 of the 660 samples as contested — an independent verifier scored them against the same rubric and disagreed with the generator.

Status, stated once. Prompt assembly, schema derivation, aggregation and turn selection are tested, and the static suite is green: 11 judge files, 10 in the default suite, 1 variant; 660 samples, all well-formed. The rubrics themselves have never scored a real transcript, and no agreement figure exists for any judge on any of the four implementations. Everything above describes what the code does, not what the judges are worth.
